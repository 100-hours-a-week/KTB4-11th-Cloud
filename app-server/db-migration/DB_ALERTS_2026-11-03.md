# DB 장애 알림 기준 및 상세 설정 (2026-11-03)

> 2026-11-03 기준 저장소의 Prometheus 알림 규칙, 수집 설정, Alertmanager 전달 설정을 정리했다. 실제 알림 전달은 모니터링 호스트의 Alertmanager 컨테이너와 SSM에 보관된 Discord webhook 설정에 의존한다.

## 1. 모니터링 구성

| 항목 | 현재 설정 |
| --- | --- |
| Prometheus 이미지 | `prom/prometheus:v3.15.0` |
| scrape 주기 | 5초 |
| rule 평가 주기 | 5초 |
| 규칙 파일 | `app-server/db-migration/plg/server/prometheus-rules/db-alerts.yml` |
| rule 파일 마운트 | `/etc/prometheus/rules/*.yml` |
| Prometheus 데이터 보존 | 최대 72시간 또는 8GB |
| MySQL 수집 | `prom/mysqld-exporter:v0.20.0`; exporter 포트 9104 |
| 알림 전달 | `prom/alertmanager:v0.28.1` → Discord |

현재 규칙 파일은 recording rule 2개와 alert 31개로 구성된다. Prometheus rule group은 `stockspoon-db-recording`, `stockspoon-mysql`, `stockspoon-proxysql`, `stockspoon-db-clock`, `stockspoon-db-primary-resources`이다.

현재 scrape 대상은 다음과 같다.

| job | 대상 | 용도 |
| --- | --- | --- |
| `mysql-primary` | Primary MySQL `3306`을 exporter의 `/probe`로 수집 | Primary 연결, 상태, heartbeat 지표 |
| `mysql-private-replica` | `mysqld-exporter:9104` | Private Replica 연결, 상태, heartbeat 지표 |
| `node` | Primary와 Private Replica의 `9100` | 호스트 시계 동기화 및 시계 차이 감지 |
| `proxysql-fargate` | Cloud Map A 레코드, ProxySQL built-in Prometheus endpoint 포트 `6070`; DNS 갱신 15초 | Fargate ProxySQL task별 상태 수집 |

MySQL 역할은 고정된 노드 이름이 아니라 `mysql_global_variables_read_only` 값으로 판단한다. `read_only=0`은 현재 쓰기 노드, `read_only=1`은 읽기 전용 노드로 취급한다.

기록 규칙 `mysql:current_primary_node`는 `read_only=0`인 DB의 안정적인 `db_node`를 node exporter의 `node_role` 라벨로 매핑한다. Primary 자원 규칙은 이 기록 규칙과 node exporter metric을 조인하므로, 고정된 EC2 이름이 아니라 switchover 이후에도 현재 쓰기 노드를 따라간다.

**Scrape**는 Prometheus가 설정된 exporter의 HTTP metrics endpoint를 주기적으로 읽어 지표를 저장하는 방식이다. 애플리케이션의 MySQL 트래픽을 ProxySQL로 보내는 동작과는 별개다. 각 scrape마다 Prometheus가 자동 생성하는 `up` 지표는 endpoint에 도달하면 `1`, scrape가 실패하면 `0`이다. 대상 자체가 설정 또는 service discovery에서 사라지면 `up` 시계열도 없어지므로 `absent()`로 별도 감지한다. [Prometheus jobs/instances](https://prometheus.io/docs/concepts/jobs_instances/), [Prometheus `absent()`](https://prometheus.io/docs/prometheus/3.12/querying/functions/#absent)

## 2. Heartbeat 지연 계산

기록 규칙 `mysql:heartbeat_lag_seconds`는 exporter의 다음 두 지표 차이를 `job`, `instance`, `db_node`별로 기록한다.

```promql
min by (job, instance, db_node) (
  mysql_heartbeat_now_timestamp_seconds{job=~"mysql-(primary|private-replica)"}
  - mysql_heartbeat_stored_timestamp_seconds{job=~"mysql-(primary|private-replica)"}
)
```

모니터링 호스트의 `pt-heartbeat` 컨테이너가 `stockspoon.monitoring_heartbeat`에 UTC 시각을 1초 간격으로 기록한다. Primary와 Replica 각각 writer 컨테이너가 있고 `--check-read-only`를 사용하므로 read-only 노드에는 기록하지 않는다. 따라서 역할 전환 후에도 새 Primary에서 heartbeat 기록이 이어진다.

두 DB 호스트와 모니터링 호스트의 시계가 동기화되어야 heartbeat 값이 유효하다. 정상이어도 writer 주기에 따라 약 0~1초 값이 관측될 수 있다.

## 3. MySQL 및 복제 알림 기준

`for`는 조건이 연속으로 유지되어야 하는 시간이다. 조건이 잠깐 발생한 것만으로는 발화하지 않는다.

| 알림 | 발화 조건 | 유지 시간 | 심각도 | 의미 |
| --- | --- | --- | --- | --- |
| `MySQLDown` | Primary 또는 Private Replica의 `mysql_up == 0` | 1분 | critical | exporter가 해당 MySQL에 연결하지 못함 |
| `MySQLExporterScrapeFailed` | `up`이 `0` (`mysql-primary` 또는 `mysql-private-replica`) | 1분 | critical | Prometheus가 mysqld-exporter HTTP endpoint에 도달하지 못함 |
| `MySQLScrapeTargetMissing` | 해당 MySQL job의 `up` 시계열에 `absent()` 적용 | 2분 | critical | Prometheus 설정/service discovery에서 수집 대상 자체가 사라짐 |
| `MySQLUpMetricMissing` | exporter scrape는 `up=1`인데 해당 job의 `mysql_up` 시계열이 없음 | 2분 | critical | exporter 응답에 MySQL 상태 지표가 누락됨 |
| `MySQLWritableNodeCountNotOne` | `read_only=0`인 수집 노드 수가 정확히 1이 아님. 시계열이 없으면 0으로 계산 | 1분 | critical | 쓰기 노드 0개 또는 2개 이상 상태 |
| `MySQLReplicationThreadStopped` | 복제 I/O 또는 SQL thread 지표가 `0` | 1분 | critical | 복제 thread 중단; 마지막 I/O/SQL 오류 번호 확인 필요 |
| `MySQLNativeReplicaLagHigh` | Private Replica의 `Seconds_Behind_Source > 30초`이고 read-only | 2분 | warning | native applier 지연이 지속됨 |
| `MySQLNativeReplicaLagCritical` | Private Replica의 `Seconds_Behind_Source > 60초`이고 read-only | 1분 | critical | native applier 지연이 심각함 |
| `MySQLReadOnlyNodeWithoutReplication` | `read_only=1`인데 해당 노드의 Replica SQL thread 지표가 없음 | 5분 | warning | 읽기 전용 노드에 복제 채널이 없는 상태 |
| `MySQLHeartbeatLagHigh` | heartbeat 지연 `> 10초`이고 노드가 read-only | 1분 | warning | Replica가 Primary heartbeat를 10초 넘게 늦게 반영 |
| `MySQLHeartbeatLagCritical` | heartbeat 지연 `> 60초`이고 노드가 read-only | 1분 | critical | 복제 지연이 심각한 상태; switchover 보류 |
| `MySQLHeartbeatWriterStale` | 쓰기 노드의 heartbeat 지연 `> 30초` | 1분 | warning | Primary heartbeat 기록이 중단되거나 갱신 지연 |
| `MySQLHeartbeatCollectorFailing` | `collect.heartbeat` exporter collector 성공 지표가 `0` | 2분 | warning | exporter가 `stockspoon.monitoring_heartbeat`를 읽지 못함 |
| `MySQLConnectionsHigh` | 연결 thread 수 / `max_connections` `> 0.8` | 5분 | warning | 연결 수가 설정 상한의 80% 초과 |

Heartbeat 및 native lag의 high와 critical이 같은 `db_node`에서 동시에 발화하면 Alertmanager가 critical을 남기고 high warning을 억제한다.

### `Seconds_Behind_Source` 의미와 한계

MySQL의 `Seconds_Behind_Source`는 현재 Replica SQL applier가 처리 중인 이벤트의 원본 기록 시각과 Replica 시각 차이를 초 단위로 보여주는 지표다. 처리 중인 이벤트가 없으면 `0`일 수 있고, 네트워크가 느리면 receiver가 늦게 받아온 relay log를 applier가 따라잡는 중이어도 `0`에 가까울 수 있다. 따라서 `0` 하나만으로 source부터의 전체 복제가 완전히 최신이라고 판단하면 안 된다. NTP 시각 변경이나 시계 skew도 정확도를 떨어뜨릴 수 있다. [MySQL 8.4 `SHOW REPLICA STATUS`](https://dev.mysql.com/doc/refman/8.4/en/show-replica-status.html)

현재 규칙은 native lag를 보조 신호로 **30초 초과 2분이면 warning, 60초 초과 1분이면 critical**로 설정했다. 별도의 end-to-end heartbeat 알림(10초/60초)과 replication I/O·SQL thread 상태도 함께 본다. 이 임계치는 낮은 복제 지연을 기대하는 현재 서비스의 초기 기준이며, 실제 write 패턴과 운영 RPO에 따라 조정한다.

## 4. ProxySQL 알림 기준

Fargate task가 ProxySQL의 built-in `admin-restapi` Prometheus endpoint를 `:6070`에 노출한다. Prometheus는 Cloud Map이 반환한 task IP를 대상으로 5초마다 지표를 읽고, 대상 IP 목록은 15초마다 DNS 갱신한다. 이 scrape는 ProxySQL 상태를 관측하는 용도이며 Backend SQL을 라우팅하거나 ProxySQL backend를 등록하는 작업은 하지 않는다. ECS bootstrap에서 `admin-restapi_enabled=true`, `admin-restapi_port=6070`으로 설정한다.

| 알림 | 발화 조건 | 유지 시간 | 심각도 | 의미 |
| --- | --- | --- | --- | --- |
| `ProxySQLScrapeDown` | `up{job="proxysql-fargate"} == 0` | 1분 | critical | ProxySQL 포트 `6070` 지표 수집 실패 |
| `ProxySQLTargetMissing` | `up{job="proxysql-fargate"}` 시계열이 없음 | 2분 | critical | Cloud Map에서 ProxySQL 수집 대상을 찾지 못함 |
| `ProxySQLNoOnlineWriter` | hostgroup `10`에 ONLINE(`status=1`) backend가 1개 미만이거나 hostgroup 지표 자체가 없음 | 30초 | critical | ProxySQL writer backend 사용 불가 |
| `ProxySQLBackendNotOnline` | ProxySQL backend 상태가 `1`(ONLINE)이 아님 | 2분 | warning | `2=SHUNNED`, `3=OFFLINE_SOFT`, `4=OFFLINE_HARD` 포함 |
| `ProxySQLConnPoolFailures` | 최근 5분 `get_conn_failure_total` 증가량이 0 초과 | 1분 | warning | backend 연결 풀에서 연결을 얻지 못한 요청 발생 |

`ProxySQLScrapeDown`은 대상 IP가 발견된 채 HTTP scrape가 실패해 `up=0`이 되는 경우를 감지한다. `ProxySQLTargetMissing`은 Cloud Map discovery 결과 job 전체에 대상이 없어 `up` 시계열이 모두 사라진 경우를 감지한다. 두 알림은 서로 다른 장애 경로를 다룬다. 현재 설정은 ProxySQL 예상 task 수를 직접 비교하지 않으므로 일부 task만 사라지고 다른 task가 scrape 중이면 그 부분 손실 자체는 알리지 않는다.

## 5. 호스트 시간 알림 기준

| 알림 | 발화 조건 | 유지 시간 | 심각도 | 의미 |
| --- | --- | --- | --- | --- |
| `DBHostClockNotSynchronised` | `node_timex_sync_status == 0` | 10분 | warning | DB 호스트 chrony가 시간 소스와 동기화되지 않음 |
| `ClockSkewFromMonitoringHost` | `abs(node_time_seconds - timestamp(node_time_seconds)) > 1` | 5분 | warning | DB 호스트와 Prometheus 수집 시각 간 차이가 1초 초과 |

시계 차이는 모니터링 호스트의 시각을 기준으로 계산한다. heartbeat 시각도 모니터링 호스트에서 기록하므로 이 값은 heartbeat 지연의 신뢰도 확인에도 중요하다.

## 6. Primary 자원 알림 및 일반 기준

다음 자원 규칙은 `mysql:current_primary_node`로 현재 `read_only=0` DB와 일치한 node exporter 시계열만 조회한다. Replica 자원은 현재 Primary가 아닌 동안 경보 대상에서 빠지고, switchover 뒤에는 자동으로 새 Primary가 경보 대상이 된다. CPU는 최근 5분 idle 비율의 평균을 사용하고, 다른 지표는 Linux node exporter의 host-level metric을 사용한다.

| 알림 | 발화 조건 | 유지 시간 | 심각도 | 확인할 항목 |
| --- | --- | --- | --- | --- |
| `PrimaryNodeExporterScrapeFailed` | Primary `node` job의 `up == 0` | 1분 | critical | node-exporter 프로세스, EC2 연결, 보안 그룹 |
| `PrimaryNodeTargetMissing` | 현재 Primary에 해당하는 `node_role`의 `up` 시계열이 `absent()` | 2분 | critical | Prometheus static target 설정 |
| `PrimaryCPUUtilizationHigh` | CPU busy `> 80%` | 10분 | warning | slow query, 동시 실행 쿼리, CPU iowait, 최근 부하 변화 |
| `PrimaryCPUUtilizationCritical` | CPU busy `> 90%` | 5분 | critical | 쿼리 부하·실행 계획 및 인스턴스 용량 |
| `PrimaryMemoryAvailableLow` | `MemAvailable / MemTotal < 20%` | 10분 | warning | MySQL buffer pool, Docker memory, swap/OOM |
| `PrimaryMemoryAvailableCritical` | `MemAvailable / MemTotal < 10%` | 5분 | critical | OOM 및 MySQL 종료 위험 |
| `PrimaryRootDiskUsageHigh` | 루트 파일시스템 사용률 `> 80%` | 10분 | warning | MySQL 데이터, binlog, Docker 로그와 증가 속도 |
| `PrimaryRootDiskUsageCritical` | 루트 파일시스템 사용률 `> 90%` | 5분 | critical | 쓰기/기동 실패 전 디스크 용량 확보 또는 확장 |
| `PrimaryRootInodeUsageHigh` | 루트 inode 사용률 `> 80%` | 10분 | warning | 작은 파일이 대량 생성되는 경로 |
| `PrimaryRootInodeUsageCritical` | 루트 inode 사용률 `> 90%` | 5분 | critical | 파일 생성 실패 위험 |

디스크 규칙은 `mountpoint="/"`를 본다. MySQL 데이터는 Docker named volume로 `/var/lib/docker/volumes` 아래에 있지만, 별도 EBS가 아니라 루트 파일시스템에 저장되므로 루트 사용률에 포함된다. 현재 Terraform 기본 루트 볼륨은 40GiB이며 크기를 변경하면 퍼센트 기준은 새 용량에 비례해 적용된다.

이 값들은 보편적인 절대 기준이 아니라 초기 운영 기준이다. Percona PMM의 기본 OS 경보도 CPU 80%, available memory 20% 기준을 제공하고, DB 연결 사용률은 80%를 기본으로 안내한다. PMM HA volume 경보는 80% 초과가 10분 지속될 때 발화한다. [Percona alert templates](https://docs.percona.com/percona-monitoring-and-management/3/alert/templates_list.html) 디스크 사용률이 100%에 가까워지면 파일시스템 고갈로 서비스 오류가 날 수 있어 90%를 critical 기준으로 추가했다. [Percona disk details](https://docs.percona.com/percona-monitoring-and-management/3/reference/dashboards/dashboard-disk-details.html)

메모리는 단순 `MemFree`나 사용률보다 Linux가 회수 가능 메모리를 고려한 `MemAvailable`을 본다. 경보를 5~10분 유지하도록 둔 것은 순간 부하에 대한 오탐을 줄이기 위한 것이다. Prometheus 문서도 특별한 사유가 없으면 alert `for` 기간을 최소 5분으로 두는 것을 권한다. [Prometheus alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/), [The Zen of Prometheus](https://prometheus.io/docs/practices/the_zen/)

운영 1~2주간 실제 시간대별 최대치와 알림 이력을 확인한 후, 반복 오탐이나 장애 탐지 지연이 있으면 임계치와 유지 시간을 조정한다. DB 자원은 CPU·메모리·디스크 외에도 connection saturation(현재 80%), 디스크 I/O latency/queue, binlog 증가율을 같이 관찰하는 것이 좋다.

## 7. 알림 전달 및 억제

설정 파일은 `app-server/db-migration/plg/server/alertmanager/alertmanager.yml`이다.

| 항목 | 설정 |
| --- | --- |
| 기본 receiver | `discord` |
| grouping key | `alertname`, `db_node`, `instance` |
| 최초 묶음 대기 | 30초 (`group_wait`) |
| 같은 묶음 갱신 간격 | 5분 (`group_interval`) |
| 반복 전송 간격 | 4시간 (`repeat_interval`) |
| 해결 알림 | 전송 (`send_resolved: true`) |
| Webhook 파일 | `/etc/alertmanager/secrets/discord-webhook` |
| Alertmanager 바인딩 | `127.0.0.1:9093` |
| Alertmanager 데이터 보존 | 72시간 |

Webhook 값은 Git이나 Terraform 설정에 저장하지 않고 SSM SecureString에서 모니터링 호스트의 파일로 가져온다. 설정은 critical/warning을 별도 Discord 채널이나 receiver로 분기하지 않고 모두 기본 Discord receiver로 전달한다.

현재 억제 규칙은 다음과 같다.

- 같은 `db_node`의 `MySQLDown`이 발화하면 해당 노드의 warning 알림을 억제한다.
- 같은 `db_node`의 `MySQLHeartbeatLagCritical`이 발화하면 `MySQLHeartbeatLagHigh`를 억제한다.
- 같은 `db_node`의 `MySQLNativeReplicaLagCritical`이 발화하면 `MySQLNativeReplicaLagHigh`를 억제한다.
- 같은 `instance`의 Primary 자원 critical 알림은 해당 자원의 warning 알림을 억제한다.

## 8. 현재 규칙의 범위와 확인 사항

- `mysql_up=0`은 exporter endpoint는 응답하지만 MySQL 연결/수집이 실패한 경우다. `up=0`은 exporter HTTP scrape 자체 실패, `absent(up)`은 해당 scrape target이 설정/discovery에서 사라진 경우, `up=1`인데 `mysql_up`이 없는 경우는 exporter 응답 지표 누락으로 각각 별도 경보한다.
- Dashboard의 native `Seconds_Behind_Source`에는 이제 보조 임계치 경보가 추가됐다. 다만 MySQL 특성상 해당 값이 0이어도 전체 지연이 0이라고 보장하지 않아 heartbeat와 thread 상태를 함께 확인한다.
- 자원 알림과 node-exporter scrape 감시는 현재 Primary만 대상으로 하며 `read_only` 역할 전환을 따라간다. Replica 자원 경보와 CPU/memory/disk I/O latency/queue 경보는 포함하지 않았다.
- `db-alerts.yml`과 Alertmanager 규칙은 코드 상태다. 현재 Prometheus에 반영하려면 모니터링 호스트에 최신 규칙·Alertmanager 설정을 배포하고 설정 reload/recreate가 필요하다. Terraform Plan/Apply 및 운영 반영은 별도로 진행한다.
